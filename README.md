# CSBS Faculty Workspace

A teacher-facing student information assistant for a third-year **Computer
Science and Business Systems (CSBS)** department.

Faculty sign in, see only the subjects assigned to them, and inspect attendance,
academic performance, assignments and extracurricular participation — either
through the application's pages or by asking an AI assistant in natural
language.

## What it does

A faculty member can:

- See a dashboard of their own subjects, computed live from the database.
- Filter, sort, search and export subject attendance, with pagination.
- Review academic performance with correct handling of missing vs. zero marks.
- Track assignment submissions, distinguishing *overdue* from *not yet marked*.
- View aggregate extracurricular participation for students they teach.
- Ask an AI assistant questions like:
  - *"Which students have less than 75% attendance in CB3202T?"*
  - *"How many consecutive classes must STU0041 attend to reach 75%?"*
  - *"Which students have overdue assignments?"*
  - *"Summarize extracurricular participation for my class."*

The assistant answers only from authorized database queries. It has no SQL
capability and cannot read a subject the signed-in teacher does not teach.

## Database schema

```
teachers ──┬──< teacher_subjects >──┬── subjects
           │                        │
           │                        ├──< attendance >──┬── students
           │                        ├──< assessments >─┼──< grades
           │                        └──< assignments >─┼──< student_assignments
           │                                           │
extracurricular_activities ──< student_activities >────┘
```

| Table | Rows | Notes |
|---|---:|---|
| `teachers` | 8 | One per distinct faculty name; one coordinator |
| `subjects` | 12 | Codes stored verbatim, including `-A` / `-F` suffixes |
| `teacher_subjects` | 12 | **Authoritative source for authorization** |
| `students` | 250 | Divisions A/B/C, year 3, semester 6 |
| `attendance` | 3,000 | One row per student–subject pair |
| `assessments` | 60 | 5 per subject, weighted |
| `grades` | 15,000 | 532 unevaluated, 312 absent, 217 genuine zeros |
| `assignments` | 36 | 3 per subject |
| `student_assignments` | 9,000 | `pending` / `submitted` / `evaluated` |
| `extracurricular_activities` | 25 | 10 categories |
| `student_activities` | 572 | 200 of 250 students participate |

**Constraints enforced in the database**, not just in application code:

```sql
CHECK (classes_conducted > 0)
CHECK (classes_attended >= 0 AND classes_attended <= classes_conducted)
CHECK (status IN ('pending','submitted','evaluated'))
CHECK (marks_obtained IS NULL OR marks_obtained >= 0)
UNIQUE (student_id, subject_code)        -- attendance
UNIQUE (teacher_id, subject_code)        -- assignments
```

### Three distinctions the schema keeps separate

These are easy to conflate and produce wrong answers when conflated:

1. **Missing mark vs. zero.** `grades.marks_obtained IS NULL` means *not
   evaluated*. A recorded `0.0` means the student attempted and scored zero.
   Performance averages exclude NULLs from the denominator; they never treat
   them as zero. The dataset deliberately contains all three states — 532
   unevaluated, 312 absent and 217 real zeros — so the distinction is exercised
   against real data rather than only in test fixtures.
2. **Absent vs. unevaluated.** `grades.is_absent` is a separate boolean, so an
   absence is distinguishable from work that simply has not been marked.
3. **Overdue vs. unmarked.** An assignment is overdue only when
   `status = 'pending' AND due_date < today`. Work that was submitted but not
   yet graded is `submitted`, never overdue.

## Authentication and permissions

### The model

| Concept | Where it lives |
|---|---|
| Teacher identity | Signed, HTTP-only session cookie (`itsdangerous`) |
| Subject scope | `teacher_subjects` table, read fresh on every request |
| Student scope | Enrollment in a subject the teacher teaches |
| Coordinator role | `teachers.is_department_coordinator` |

Every request follows the same path:

1. Read the signed cookie → teacher ID. **A teacher ID in a request body, query
   string or chat message is never consulted.**
2. Load a `TeacherPrincipal` with subjects resolved from the database.
3. Authorize the requested subject or student against that scope.
4. Query only authorized records.
5. Return only permitted fields.

### What is enforced

- A teacher can open their own subjects; another teacher's subject returns
  **403**.
- A student is reachable only if enrolled in a subject the teacher teaches.
- A nonexistent subject and a forbidden subject both return **403**, so the
  endpoint cannot be used to enumerate the catalogue.
- Department-wide extracurricular reporting requires the coordinator role.
  Teaching one subject does **not** imply department-wide access.
- CSV export applies the same authorization and the same filters as the table
  on screen.
- The 13 AI tools re-check scope against the database on every call. The model
  is never trusted to have respected its instructions.

The system prompt is a **behavioural** control. Authorization is enforced in
`app/core/security.py` and in every tool, independently of what the model does.

### Attendance arithmetic

All attendance maths lives in **one module**, `app/services/attendance_math.py`,
and uses `Fraction` so results never drift with floating point:

```python
attendance_percentage = classes_attended / classes_conducted * 100
```

For a target `T`% with `A` attended of `C` conducted, the minimum number of
consecutive future classes that must all be attended:

```
n = max(0, ceil((T·C − A·100) / (100 − T)))
```

Edge cases are handled explicitly: a target of 100% after any absence raises an
error rather than returning a number; `30/40` is exactly 75% and is **not**
counted as below a 75% threshold.

The **75% threshold is a configurable demonstration setting** (`ATTENDANCE_THRESHOLD`),
not a verified college regulation. The UI and the assistant both say so.

### Averages: which one is shown

Two different averages are reported, each labelled in the UI:

- **Pooled / class attendance** — `sum(attended) / sum(conducted)`. Every
  *class* counts equally.
- **Mean student percentage** — the unweighted mean of each student's own
  percentage. Every *student–subject record* counts equally.

They differ whenever subjects have different class counts, which is why both are
shown rather than one unlabelled "average".

## Local setup

**Prerequisites:** Python 3.12, Node.js 20+, and a PostgreSQL database
(this project was developed against [Neon](https://neon.tech)).

### 1. Clone and configure

```powershell
# Windows PowerShell
git clone <your-repo-url>
cd "AI Project"
Copy-Item .env.example backend\.env
```

```bash
# macOS / Linux
git clone <your-repo-url>
cd "AI Project"
cp .env.example backend/.env
```

Edit `backend/.env`:

```dotenv
DATABASE_URL=postgresql+psycopg://user:password@host/dbname?sslmode=require
SESSION_SECRET=<paste a generated secret>
FRONTEND_ORIGIN=http://localhost:3000
ATTENDANCE_THRESHOLD=75
COOKIE_SECURE=0
```

Generate a session secret:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

> **No AI provider key is needed here.** Keys are supplied by each teacher at
> runtime through Settings. The dashboard, the database and the seed scripts all
> work without one.

### 2. Backend

```powershell
# Windows PowerShell
cd backend
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

```bash
# macOS / Linux
cd backend
python3.12 -m venv .venv
source .venv/bin/activate

```

### 3. Database

```powershell
# Create the schema
alembic upgrade head

# Generate the CSVs (optional: they are committed)
python scripts/generate_dataset.py

# Load the CSVs into PostgreSQL
python scripts/seed_database.py
```

The seed script is idempotent — it clears and reloads, so re-running always
leaves the database matching the CSVs. It verifies row counts and attendance
constraints before finishing.

### 4. Run the backend

```powershell
uvicorn app.main:app --reload --port 8000
```

API docs: <http://localhost:8000/docs>

```powershell
cd frontend

"NEXT_PUBLIC_API_BASE_URL=http://localhost:8000" | Out-File -Encoding utf8 .env.local
npm run dev
```

```bash
# macOS / Linux
cd frontend

echo "NEXT_PUBLIC_API_BASE_URL=http://localhost:8000" > .env.local
npm run dev
```

Open <http://localhost:3000> and pick a faculty member.


## AI providers and BYOK

Teachers supply their own API key in **Settings**. Nine providers are supported:

| Provider | Key required | Custom endpoint | Tool calling |
|---|:--:|:--:|:--:|
| OpenAI | ✔ | ✔ | ✔ |
| Anthropic | ✔ | — | ✔ |
| Google Gemini | ✔ | — | ✔ |
| Groq | ✔ | — | ✔ |
| OpenRouter | ✔ | ✔ | varies by model |
| DeepSeek | ✔ | ✔ | ✔ (not `deepseek-reasoner`) |
| Together AI | ✔ | ✔ | ✔ |
| Ollama | — | ✔ | ✔ |
| Other OpenAI-compatible | ✔ | required | ✔ |

DeepSeek, OpenRouter, Together and other OpenAI-style services use
`langchain-openai` with a custom `base_url`; no extra packages are needed.

### How your key is handled

- Held in the browser tab's React state **only** — never `localStorage`, never a
  cookie, never a URL.
- Sent to the backend with a chat or test request, used to construct a client
  for that one call, then discarded. Nothing is cached between requests.
- **Never written to PostgreSQL**, chat history, analytics or logs.
- Redacted from log output and from error messages
  (`app/core/logging.py`, `sanitize_provider_error`).
- Never returned to the browser.
- Cleared on sign-out and on page reload. This is a deliberate trade-off:
  convenience is sacrificed so a key cannot outlive the session.

Provider errors are translated into something actionable — *"The provider
rejected the API key"* — rather than echoing a raw SDK exception that may
contain the `Authorization` header.

### Ollama

Works locally for development:

```bash
ollama serve
ollama pull llama3.1
```

Then set the endpoint to `http://localhost:11434` in Settings.

> **Deployment limitation.** `localhost:11434` is resolved by the **backend**,
> not the browser. A deployed backend cannot reach a teacher's personal machine.
> For deployed use, point the endpoint at a network-reachable Ollama service or
> Ollama Cloud. Do not expose an unauthenticated Ollama instance to the public
> internet.

### Endpoint validation (SSRF)

Custom endpoint URLs are validated before any request is made
(`app/ai/provider_factory.py`):

- Only `http` / `https`.
- The hostname is resolved and **every** returned address is checked. Private,
  loopback, link-local, reserved and multicast addresses are rejected — this
  blocks cloud metadata endpoints such as `169.254.169.254`.
- Remote providers must use `https`.
- Loopback is permitted **only** for Ollama, which is the documented local
  development case.

## LangChain integration design

```
ChatRequest ──► provider_factory.build_chat_model()   # per request, no caching
                        │
                        ▼
           model_registry.supports_tools(provider, model)
                 │                           │
         tool calling                 no tool calling
                 │                           │
                 ▼                           ▼
     bind_tools(13 scoped tools)   aggregate-only context in the prompt
                 │                           │
                 └──────────┬────────────────┘
                            ▼
                     model.astream()  →  SSE token frames
```

### The 13 tools

Each is a fixed, parameterized operation bound to one `TeacherPrincipal` and one
database session. **There is no SQL tool and no write tool.**

`get_teacher_subjects` · `get_subject_attendance_summary` ·
`get_low_attendance_students` · `get_student_attendance` ·
`get_classes_needed_for_target` · `get_subject_performance_summary` ·
`get_students_below_marks_threshold` · `get_assignment_submission_summary` ·
`get_student_assignment_status` · `get_extracurricular_summary` ·
`get_student_extracurricular` · `get_student_academic_summary` ·
`find_students`

Every tool re-checks authorization before reading. A subject code or student ID
the model invents simply fails and returns a refusal the model must relay.

Results are capped at 40 rows and disclose truncation, so the assistant cannot
claim to have analyzed everyone when it saw a subset. Tool results also carry
the relevant definitions (the threshold used, what "overdue" means, how missing
marks were handled) so the model restates them correctly.

### Models without tool calling

`deepseek-reasoner`, `o1-mini` and `o1-preview` are flagged in the registry. For
these, the backend fetches an **aggregate-only** snapshot of the teacher's
subjects and places it in the prompt — no per-student rows ever enter the
context — and the assistant tells the teacher that per-student answers need a
tool-calling model.

### System prompt

Version-controlled at `backend/app/prompts/teacher_assistant.py` and applied
server-side only. It is composed per request with the **session-established**
teacher identity, their resolved subjects, and the configured threshold.

The full student dataset is never placed in the prompt.

## Streaming

`POST /api/chat` returns Server-Sent Events. Tokens are forwarded as the
provider emits them — nothing is buffered to completion, and there is no
simulated typing animation.

| Event | Payload | Meaning |
|---|---|---|
| `status` | `{state: "thinking" \| "streaming"}` | Phase change |
| `tool` | `{name, state: "running" \| "complete" \| "denied"}` | Tool activity |
| `token` | `{text}` | A chunk of generated text |
| `error` | `{message, kind}` | Sanitized failure; terminal but retryable |
| `done` | `{ok}` | Stream finished |

Implemented on both sides:

- Progressive rendering, one frame per provider chunk
- **Stop** via `AbortController`; partial text is kept
- Server-side disconnect detection, so an abandoned request stops upstream work
- **Retry** of the last user turn, discarding the failed reply
- Correct ordering, no duplicate responses
- Provider/model switching and conversation clearing
- Visible generation status and tool badges
- Request-size limits (256 KB body, 8,000 chars/message, 40 messages)
  and upstream timeouts
- `X-Accel-Buffering: no` so proxies do not buffer the stream

A failed provider call surfaces an error and a Retry button. **It is never
replaced with a fabricated answer.**

## Deployment

### Frontend → Vercel

```bash
cd frontend
vercel
```

Set `NEXT_PUBLIC_API_BASE_URL` to the deployed backend URL.

`frontend/vercel.json` pins the framework and adds security headers.

### Live deployment

| | URL |
|---|---|
| Frontend | https://frontend-kappa-puce-90.vercel.app |
| Backend | https://csbs-faculty-api.vercel.app |
| Database | Neon PostgreSQL |

Both run on Vercel. `backend/api/index.py` is the serverless entrypoint; Vercel
detects FastAPI and serves the ASGI app directly, so **no rewrite rule is
needed** — adding one rewrites the request path itself and makes every route
404.

> **Serverless caveats, measured not assumed.** The health check, session
> cookies, authorization and all data endpoints work correctly. But this
> backend was designed for a long-running process, and on serverless:
> SSE streaming is bounded by the 60 s function limit, so a long model turn can
> be truncated; the SQLAlchemy pool cannot persist across invocations, so a
> pooled Neon connection string is required; and the in-process rate limiter
> keeps per-instance counters, so limits are much weaker than configured.
> `backend/render.yaml` and `backend/Dockerfile` remain the better choice when
> reliable streaming matters.

### Backend → a Python host

FastAPI with SSE streaming and a persistent connection pool is better suited to
a long-running process than to serverless functions. **Render, Railway, Fly.io
or any container host** are good fits.

```
Build:  pip install -r requirements.txt
Start:  uvicorn app.main:app --host 0.0.0.0 --port $PORT
```

Two manifests are provided:

- `backend/render.yaml` — a Render blueprint with a health check and
  `SESSION_SECRET` generated automatically.
- `backend/Dockerfile` — a non-root Python 3.12 image with a health check, for
  any container host.

Environment variables:

```dotenv
DATABASE_URL=postgresql+psycopg://...
SESSION_SECRET=<a strong secret>
FRONTEND_ORIGIN=https://your-app.vercel.app   # exact origin, no trailing slash
ATTENDANCE_THRESHOLD=75
COOKIE_SECURE=1                                # required for cross-site cookies
```

> **Cross-site cookies.** With the frontend on Vercel and the backend elsewhere,
> the session cookie must be `SameSite=None; Secure`. Setting `COOKIE_SECURE=1`
> does this. Both must be served over HTTPS, and `FRONTEND_ORIGIN` must match
> the deployed origin exactly — CORS uses that value and never a wildcard,
> because the cookie is credentialed.

Run migrations once against the production database:

```bash
alembic upgrade head
python scripts/seed_database.py
```

### Database → Neon

Create a project, copy the pooled connection string into `DATABASE_URL`.
`pool_pre_ping` and `pool_recycle=280` are configured because Neon's pooler
closes idle connections.

## Security

| Control | Implementation |
|---|---|
| Server-side authorization | `TeacherPrincipal`, checked on every route and tool |
| Session integrity | `itsdangerous` signed cookie, HTTP-only, 8-hour expiry |
| Least privilege | Subject scope from `teacher_subjects`; student scope from enrollment |
| Parameterized queries | SQLAlchemy Core/ORM throughout; no string-built SQL |
| Input validation | Pydantic v2 + regex-constrained path parameters |
| Credential redaction | Regex filter on all log records; sanitized provider errors |
| Safe Markdown | `react-markdown` (no `dangerouslySetInnerHTML`, no raw HTML) |
| Prompt-injection defense | Only `user`/`assistant` roles accepted; tool results treated as data; authorization independent of the prompt |
| Request-size limits | 256 KB body; 8,000 chars/message; 40 messages |
| Upstream timeouts | 120 s default, configurable |
| Rate limiting | 20 chat/min, 240 API/min, 30 sessions/min per client |
| Cache headers | `no-store` on all `/api/*` except health |
| CORS | Exact origin only, credentials enabled, no wildcard |
| Error handling | Generic 500s; stack traces logged, never returned |
| Security headers | `nosniff`, `no-referrer`, `X-Frame-Options: DENY` |

> **Rate-limiting caveat.** The limiter is in-process and is adequate for a
> single-instance demo. A multi-instance deployment needs a shared store such as
> Redis, since each instance currently keeps its own counters.

> **Dependency audit.** `npm audit` reports advisories in
> `eslint-config-next`'s transitive dependencies (`braces` → `micromatch` →
> `fast-glob`). These are **development-only** lint-time packages and ship
> nothing to the browser. `npm audit fix --force` downgrades Next.js to v14, so
> they are left in place deliberately.

## Troubleshooting

**`Could not reach the backend`**
Confirm the backend is running on port 8000 and that
`frontend/.env.local` has the right `NEXT_PUBLIC_API_BASE_URL`.

**401 on `/api/teachers/me` right after loading the page**
Expected before sign-in — the app probes for an existing session.

**403 opening a subject**
Working as intended. That subject belongs to another faculty member. Sign in as
the teacher who teaches it.

**`server closed the connection unexpectedly`**
A stale pooled connection. `pool_pre_ping` and `pool_recycle=280` handle this;
if it persists, lower `pool_recycle`.

**`alembic upgrade head` hangs**
Check `DATABASE_URL`, and that the host allows connections from your network.
Neon requires `?sslmode=require`.

**Seed script: "Missing …csv"**
Run `python scripts/generate_dataset.py` first.

**Assistant says no provider is configured**
Open **Settings**, choose a provider, enter a key, then **Activate provider**.
The key clears on reload — this is deliberate.

**Ollama connection refused**
The backend, not the browser, must reach the endpoint. A deployed backend cannot
reach your laptop.

**Cookies not persisting in deployment**
Set `COOKIE_SECURE=1`, serve both sides over HTTPS, and make `FRONTEND_ORIGIN`
exactly match the frontend origin.

## Before using real college records

This project is **not ready for real student data.** At minimum, the following
would be required:

**Authentication and identity**
- Replace the demo selector with real authentication — institutional SSO
  (SAML/OIDC), MFA, proper session lifecycle and revocation.
- Remove `/api/demo-teachers` and `/api/demo-session` entirely.

**Authorization**
- Review the scope model against the institution's actual policy. The current
  rule — *a teacher sees students enrolled in subjects they teach* — is a
  reasonable default, not a policy decision.
- Add explicit roles for HoD, mentors, exam cells and administrative staff.

**Audit and accountability**
- Log every access to a student record: who, what, when, why. None of this
  exists today.
- Add retention and deletion policies.

**Privacy and compliance**
- A data protection impact assessment under the applicable regime (in India, the
  DPDP Act 2023).
- A lawful basis for processing, and a decision on whether students are informed
  that an AI assistant can summarize their records.
- A policy on sending student data to third-party AI providers. **Every chat
  sends authorized query results to whichever provider the teacher configured.**
  This may be unacceptable without a data processing agreement, or may require
  restricting providers to self-hosted models.

**Operational**
- Shared-store rate limiting; secrets in a managed vault.
- Backups, disaster recovery, monitoring and alerting.
- Penetration testing and a security review.
- Accessibility audit against WCAG 2.1 AA.

**Correctness**
- The 75% threshold must be replaced with the institution's actual regulation,
  including any subject-specific or condonation rules.
- Verify that attendance semantics match institutional practice (what counts as
  a conducted class, how labs are weighted, how medical leave is treated).
